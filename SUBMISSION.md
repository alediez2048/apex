# Submission — Apex Mobile Check Deposit System

## Project Name

Apex Mobile Check Deposit System

## Summary

A complete mobile check deposit processing system built as a single Go binary with an embedded web UI, SQLite persistence, and zero external dependencies. The system implements the full deposit lifecycle — submission, vendor validation (7 deterministic scenarios), funding business rules (limits, eligibility, 30-day duplicate detection), double-entry ledger posting with balanced DEBIT/CREDIT pairs, risk-scored operator review queue with check image display, X9 ICL-structured JSON settlement batching with EOD cutoff logic, and post-settlement return/reversal processing with $30 fee application. All financial mutations execute within single database transactions to preserve ledger invariants.

## How to Run

```bash
# Prerequisites: Go 1.21+, CGO-enabled C compiler, jq (for demo)

# Clone and start
git clone https://github.com/alediez2048/apex.git
cd apex
make dev
# Server starts at http://localhost:8080

# Run all tests
make test

# Run the full self-contained demo (builds, starts server, runs 6-act demo, stops)
make demo-full

# Generate coverage report
make report
```

## Risks and Limitations

**SQLite single-writer constraint.** All write operations serialize through a single database connection. This is correct for financial invariants but limits throughput to ~100-200 write transactions/second. Production deployment would require migration to PostgreSQL with row-level locking.

**Vendor stub is not a real integration.** The deterministic scenario engine (magic prefixes) enables testing and demos but doesn't exercise real network error handling (timeouts, retries, circuit breaking). A production vendor integration would need retry policies, idempotency keys, and webhook-based async responses.

**TOCTOU window in return processing.** The return handler reads transfer state and writes within the same transaction, but `GetTransfer` uses a plain `*sql.DB` query rather than a transactional read. Under SQLite's single-writer model this is safe, but a PostgreSQL migration would need `SELECT ... FOR UPDATE` or a transactional read.

**Risk scoring is single-signal.** Only vendor confidence drives the flag/approve decision. A production system would incorporate deposit amount thresholds, account history, velocity checks, and potentially third-party fraud scoring.

**No TLS or production hardening.** The server listens on plain HTTP. Production deployment would require TLS termination (reverse proxy or built-in), CORS configuration, CSP headers, and rate limiting.

**Business day calculation excludes holidays.** Settlement date rollover only accounts for weekends. Federal Reserve holidays (e.g., MLK Day, Presidents' Day) are not excluded, which could result in settlement dates falling on non-processing days.

## How Should ACME Evaluate Production Readiness?

1. **Ledger invariant verification.** Run `SELECT SUM(CASE WHEN entry_type='DEBIT' THEN amount ELSE 0 END) - SUM(CASE WHEN entry_type='CREDIT' THEN amount ELSE 0 END) FROM ledger_entries` — the result must be exactly zero. This is the single most critical correctness property.

2. **State machine completeness.** Verify that no transfer exists in a state without a corresponding `deposit_events` trail. Every state transition should have an event with actor attribution.

3. **Settlement reconciliation.** For each settlement batch, verify that `file_control.total_amount` equals the sum of all included check detail amounts, and that no transfer appears in more than one batch.

4. **Return atomicity.** Process a return and verify that exactly 4 ledger entries are created (2 balanced pairs) and the transfer status is `Returned` — all within a single transaction. Simulate a crash mid-return and verify no partial state exists.

5. **Duplicate detection coverage.** Submit the same check (same MICR routing + account + check number + amount) twice within 30 days and verify the second is rejected with `FUNDING.DUPLICATE`.

6. **Demo reproducibility.** Run `make demo-full` from a clean state — all 24 assertions should pass. Run it again — same result. The system should be fully deterministic with no time-dependent flakiness.

7. **Load and concurrency testing.** Under concurrent API requests, verify that the ledger invariant holds and no double-batching occurs. SQLite's `BEGIN IMMEDIATE` serialization should prevent corruption, but throughput limits should be benchmarked.

## Architecture Choices, Vendor Stub Design, and State Machine Rationale

**Single binary architecture.** Go's `embed` directive packages HTML/CSS/JS directly into the compiled binary, eliminating deployment complexity. The entire system — API server, web UI, database migrations, and demo seed data — ships as one executable with no external dependencies beyond a C compiler for SQLite.

**Deterministic vendor stub.** Rather than random outcomes or configuration-driven mocking, the vendor stub uses account ID prefixes (`PASS-`, `BLUR-`, `GLARE-`, etc.) to select scenarios. This makes every test and demo fully reproducible: `BLUR-20001` always fails with IQA blur, `MICR-10001` always flags for operator review. The `X-Vendor-Scenario` header override allows ad-hoc testing of any scenario against any account. MICR data (routing number, account number, check number) is generated deterministically from the account ID, enabling predictable duplicate detection testing.

**8-state lifecycle with explicit Approved.** The state machine always persists the `Approved` state, even for auto-approved deposits. This ensures every transfer has a complete audit trail: `Requested → Validating → Analyzing → Approved → FundsPosted`. Skipping `Approved` would create a phantom state — the deposit would appear to jump from `Analyzing` to `FundsPosted` with no record of the approval decision. Terminal states (`Rejected`, `Returned`) are enforced at the domain level and cannot transition further.

**Double-entry ledger with transaction-scoped posting.** Every financial operation creates exactly balanced DEBIT/CREDIT pairs within a single `BEGIN IMMEDIATE` transaction. Returns create 4 entries (reversal pair + fee pair) atomically. The invariant `SUM(debits) == SUM(credits)` is verified in integration tests and can be checked against the live database at any time.
